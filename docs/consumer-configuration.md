# Consumer configuration

Every knob a consumer of Agent Kit can configure or personalize, in one place: where it is defined, what reads it, whether the Mission Control Config tab can write it, and the copy-paste snippet to use when the tab write path is unavailable (server down, non-loopback, read-only deploy).

## Where configuration lives

| Layer | Location | Scope |
|-------|----------|-------|
| Session config | `.cursor/context/config.json` (template: `.cursor/context/config.example.json`) | Per-workspace agent behavior and Mission Control prefs |
| Dashboard skin | Browser `localStorage` key `agent-kit:dashboard-skin` | Visual chrome of Mission Control only; never written to the repo |
| Install manifest | `.cursor/agent-kit.json` | What the installer laid down (profile, skills, packs, registry ref) |
| Personalization result | `.cursor/context/personalization.json` | What the personalization generator applied or skipped |
| Repo profile | `.cursor/agent-kit.config.json` | Scanner-detected repository profile; read-only, regenerated by scan |

## Repo profile (mostly read-only; three confirmable overrides)

`.cursor/agent-kit.config.json` is the scanner-detected profile (purpose, stack, git, infra, services, context sources). Most of it is regenerated by every scan (`agent-kit doctor`, `agent-kit doctor --refresh-profile`, `agent-kit doctor --fix-safe`) and stays out of Config-tab scope by design — hand-editing most fields has no lasting effect. Three subkeys are the exception: `purpose.value` (+ `categories`/`evidence`), `git.provider` (+ `providerKind`), and `stack` (`language` plus at least one of `testCommands` / `validationCommands`) are read as an **operator confirmation** before the corresponding auto-detector runs; once set, the confirmed value is the source of truth on every later scan (the detector does not silently reclassify it) and the same value round-trips back into this file, so it survives. There is no dedicated CLI setter for any of the three — set them by editing the JSON file directly, same mechanism for all three keys. `stack` parity with `purpose`/`git.provider` closes a gap where a repository whose language the scanner cannot detect (no recognized manifest, or one that lives under a subdirectory the scan does not reach) had no way to be told "this is Dart, test with `dart test`" (dogfood/cursor_stack_detection_no_dart_flutter_subdir_override_2026_09_15.md, defect 3).

#### `agent-kit run-plan` detail

`--backend claude` runs each tick as headless `claude -p` under the same one-tick contract as `cursor-agent` (one to-do, `LOOP_TICK_RESULT` sentinel, `/git-staging` on a diff, never `/git-prod`). Implemented 2026-09-06 (plan `major-tom` Phase 1, ADR `2026-09-04_major-tom-autonomous-mode.md`; fulfils the reservation in ADR `2026-08-13_claude-cli-ultracode-orchestration-thin-adapter.md:13`). Select it with `--backend claude`, or `--backend auto` on a machine where `cursor-agent` is absent and `claude` is on PATH (default stays `cursor-agent`).

Gateway routing: set `ANTHROPIC_BASE_URL` (endpoint) and `ANTHROPIC_AUTH_TOKEN` (sent as `Authorization: Bearer`) in the runner environment; leave `ANTHROPIC_API_KEY` unset when using a bearer gateway.
Both values (and `ANTHROPIC_API_KEY`) are redacted in every tick log, CLI tip and error string (`.cursor/loop-logs/tick-*.log`) on every backend: `cursor-agent` does not read them, but its child inherits the runner environment, so the same redaction list applies to its tee.
Redaction is exact-substring and covers the value plus its enumerable derived forms: for `ANTHROPIC_BASE_URL` the trailing-slash variant, origin, `host:port` and hostname (so a gateway-down `connect ECONNREFUSED host:port` line does not print the gateway address; `localhost`-style and sub-4-char hostnames are not derived); for the token and key the common encoded forms (JSON-escaped, URL-encoded, base64 and base64url at value start, i.e. the value encoded on its own).
A form that cannot be enumerated (an abbreviation, a hash) is not covered. Redaction is chunk-boundary safe, so a value split across two output chunks is still elided whole.
Nested sessions: the child env drops `CLAUDECODE`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_CHILD_SESSION` and `CLAUDE_CODE_BRIDGE_SESSION_ID` (the same four the `claude` CLI removes before spawning its own children), so a loop started from inside a Claude Code shell does not classify as a nested child.
Anthropic-protocol endpoints only (`ANTHROPIC_BASE_URL`); no second ACP listener and no `--backend deepseek` — see ADR 2026-08-22 deepseek-harness concept #9.

Headless permission caveat: `claude -p` starts read-only and has no one to answer prompts, so the backend passes `--dangerously-skip-permissions --permission-prompts none` (bypass everything, deny anything that would still prompt, no AskUserQuestion); do not run it against a tree you have not reviewed.
Requirements checked before spawn: `claude >= 2.1.259` (`--permission-prompts`; an older binary is refused with a `claude update` hint instead of a bare exit 1) and the Claude Code slash adapter `.claude/commands/run-plan.md` in the workspace (generated by `agent-kit install --claude`; without it the tick prompt's leading `/run-plan` would be sent as literal text, so the backend fails closed).
Runaway caps are opt-in: `AGENT_KIT_CLAUDE_MAX_TURNS=<int>` and `AGENT_KIT_CLAUDE_MAX_BUDGET_USD=<number>` map to `--max-turns` / `--max-budget-usd`; unset means no cap (parity with `cursor-agent`).
A tick whose stream-json result carries `is_error` (`error_max_turns`, `error_max_budget_usd`, `error_during_execution`, e.g. a gateway 401) stops the loop with that subtype named on the console instead of a generic no-sentinel or exit-code message.

Two different fields share the value `claude`: `agent-kit run-plan --backend auto|cursor-agent|claude` is a CLI flag that selects the agent that **implements** each headless tick (`cursor-agent -p ...` or `claude -p ...`); `externalPlanReview.backend: auto|claude|cursor|cloud` is a `.cursor/context/config.json` key that selects the post-hoc audits **reviewer** launched by `.cursor/scripts/plan-external-review.sh` after a plan exhausts.
They are read by different code, accept different value sets (note `cursor-agent` vs `cursor`), and are never merged or inferred from one another.
They interact only through the same-model rule: when ticks run with `--backend claude`, a reviewer pinned to `claude` (or `auto` resolving to Claude) is the honest same-model skip and the Field Report stays owed; `preflight: warn|block` surfaces that combination with the same outs (`backend: "auto"`, `"cursor"`, or `"cloud"`).
Distinct from `agent-kit run`, which spawns `claude` for a one-shot L0 prompt with the same env passthrough and log redaction (`.cursor/loop-logs/run-*.log`).

**Terminal rendering:** on a TTY (both backends) the run shows the Mission Control live view — progress bars for the current plan's to-dos and, on `run-plan-all`, the plan queue read from HANDOFF `Run queue` / `Queue cursor`; a scrolling Flight Log of rendered status lines (assistant text, one-line tool-call / tool-result summaries, hook lines, rate-limit warnings, the final result); and a Crew Monitor for backend/pid/elapsed/cost.
`--plain` forces status lines instead (always the case on a non-TTY, `NO_COLOR`, or `CI`); the `.cursor/loop-logs/` file always keeps the complete NDJSON regardless of rendering mode.

**HITL relay and transport:** reaching a numbered-list gate (sentinel line `HITL_GATE: <ask-id> | <label 1> | ... | <label n>`, prose fallback otherwise) pauses the run, shows the options in the terminal or TUI, and reads one line from stdin (a number or an exact label); the reply is delivered to the same agent session (the `claude` backend keeps one `--input-format stream-json` child per run with stdin open and relays the reply as a `user` event; `cursor-agent` has no such relay yet, so a gate there is an honest stop) and stamped `HITL_REPLY: <ask-id> | operator reply <n> | <label>` in both the terminal and the NDJSON log.
Empty input, EOF, `skip`, `cancel`, or Ctrl-C stop the run with `stopped-by-operator` (exit code from `hitlExitCode`); a non-TTY stdin without `--no-hitl` stops the same way.
`--no-hitl` is the CI opt-out: reaching a gate stops the run immediately with `stopped: unanswered gate` and never supplies a default answer. The relay never answers a gate on its own, and `git-prod` / `kit-prod` gates are always refused regardless of `--no-hitl`.
Decision record: ADR `2026-09-19_headless-hitl-transport-and-live-tui.md` (amends point 7 of ADR `2026-08-27_cli-native-mission-control-tui-thin-deps-third-surface.md` to cover this headless lane; dependency lock unchanged, no new runtime dependency).

## How the Config tab saves

The Config tab (Mission Control, More menu) renders five fieldsets (Read-only, Session, Update check, Audits, Agent Personas) and saves through `PATCH /api/config` on the loopback server:

- **Allowlist-only:** unknown top-level or nested keys are rejected with 400 (`validateConfigWriteBody` in `dashboard/lib/guards.mjs`).
- **Merge-safe:** the patch merges into the existing file; non-editable nests are preserved (`mergeConfigAllowlist`).
- **Loopback-only:** the remote address must be loopback; the LAN broadcast token never unlocks writes (`handleConfigWrite` in `dashboard/serve.mjs`).
- **Path-locked:** writes go only to `.cursor/context/config.json` under the snapshot repo root (`resolveContextConfigPath`).
- **`updateApply.auto` is never writable** through this API. Keep it `false` unless you accept silent L0 overwrite risk; change it only by editing `config.json` by hand (or via explicit `/update` / CLI apply flows).

## When the write path is unavailable

If the dashboard server is down, the panel is reached over LAN (writes stay loopback-only), or the deploy is read-only:

1. Open `.cursor/context/config.json` in the editor.
2. Paste the snippet from the table above and merge it into the existing object (snippets are fragments, not full files).
3. Save. Chat commands and the CLI read the file on the next tick; Mission Control reflects the change on the next snapshot refresh.

The Config tab also offers per-fieldset copy-snippet buttons that place the same fragments on the clipboard. Copy-only: snippets never write anything by themselves.

## Constraints (by design)

- Widening the write allowlist requires a new decision record, not a side effect of other work (`.cursor/memory/decisions/2026-07-26_mission-control-config-write-allowlist.md`).
- UI CTAs in Mission Control are copy-only; `/api/config` is the single narrow write exception (`.cursor/memory/decisions/2026-07-25_mission-control-copy-only-paste-destinations.md`).
- Interface Skins stay localStorage-only and out of repo config.
- The repo profile (`.cursor/agent-kit.config.json`) is read-only for consumers.
